## 0. 迭代工作流（每次迭代必须遵守）

1. **开工前**：先 `git pull`，读 `docs/DEVLOG.md` 与本文档相关章节。
2. **改动范围**：遵守「最小写集」，优先抽 `src/domain/` 纯函数并配单测；UI 改动沿用现有 design token 与 SVG 图标体系。
3. **测试**：新逻辑必须补 Vitest 用例（`src/test/*.test.ts`）；跑 `npm test` 全量回归。
4. **构建**：`npm run build`（含 `tsc -b` 类型检查）必须成功。
5. **浏览器冒烟**：`npm run preview` 后 Playwright 验证关键路径（见 DEVLOG §0），要求**零 console/page error**。
6. **提交推送**：`git commit` + `git push origin main`（分支默认 `main`，若需实验分支用 `codex/` 前缀）。
7. **发布**：按 DEVLOG §0 流程 `promote-release.sh` 部署并做线上验证。
8. **文档**：更新本文档状态、`deepseek-version-optimize.md` 状态表、`docs/DEVLOG.md` 新增条目。

**全局验收闸门**（任何迭代合入前）：`npm test` 全绿 + `npm run build` 成功 + 冒烟零报错 + 线上 hash 资源全部 200。

### 1.4 cover/contain 焦点控制（P1，✅ 2026-08-03 已发布）

- **现状**：`src/components/CropDialog.tsx` 的 cover/contain 总是几何居中裁剪，主体（人脸/主体物）偏一侧时会被切边；仅做了 UI 层优化，焦点算法未深改。
- **目标**：裁剪以「焦点」为锚点而非几何中心。
- **方案**：
  1. 焦点来源 A（手动）：在裁剪预览图上点击设定焦点（十字标记）。
  2. 焦点来源 B（自动）：显著度先验 —— 对降采样图计算边缘密度/饱和度加权热区，或复用 `@imgly/background-removal` 的 alpha 掩码取前景质心；无显著前景时回退几何中心。
  3. 在 `src/domain/conversion.ts` 或新 `src/domain/focus.ts` 实现纯函数 `computeCropRect(source, focus, mode, targetAspect)`：给定焦点像素坐标与 cover/contain 模式，返回裁剪窗口，保证焦点落在窗口内的黄金分割位置附近，且窗口不越界。
  4. CropDialog 展示焦点与最终窗口预览。
- **验收**：人脸偏左 25% 的测试图，cover 模式裁剪后主体完整（人脸中心在窗口内）；`focus.ts` 单测覆盖越界/极角/等比缩放情形。
- **风险**：显著度自动检测可能误判；手动焦点优先级最高，自动仅为默认值。
- **实施结果**：新增 `src/domain/focus.ts`；cover 采样与 CropDialog 共用自动/手动焦点及裁剪窗口。对话框支持点击、方向键、恢复自动焦点和最终窗口预览，手动框选保持最高优先级。
- **验证**：`focus.test.ts` 7 例覆盖 contain、等比例、黄金分割、极角钳制、平坦图回退、偏侧显著主体和 cover 重采样；`crop-dialog.test.tsx` 覆盖指针与键盘交互。

### 1.10 裁剪像素画智能尺寸恢复（P0，✅ 2026-08-03 已发布）

- **问题**：合照裁剪出的像素角色常经过非整数倍缩放，7.5px 基础格会交替呈现为 7/8px；旧算法只识别 15px 倍频且偏向最大的可信周期，因此把应为约 23×31 的角色生成为 11×15。
- **实施结果**：`estimatePixelArtScale` 改为在可信候选中选择增益最强的基础周期，并通过横纵方向的平衡双相位检测恢复半周期；`analyzeSource` 与实际转换共用结构化像素画识别，避免推荐“照片平滑”与转换器像素恢复互相矛盾；设置面板显示检测结果、实际逻辑尺寸及 52 针上限说明。
- **验证**：新增 9px/18px 倍频竞争、7.5px 非整数重采样、推荐分类一致性与尺寸说明回归。全量测试 166/166；实际用户裁剪图在本地和生产站均输出 23×31，应用智能推荐后尺寸不变，控制台零错误。
- **发布**：commit `88e68d3` 已推送并原子发布；回滚备份 `/var/www/image2pindou.backup-20260803-222001`。

### 1.11 角色原图 → 多尺寸精细图纸（2026-09-07，已发布）

- **需求边界**：用户确认主要上传角色原图，参考图是输出效果；不做带网格/色号截图的 OCR 还原，也不引入云端上传或角色重绘。
- **尺寸**：新增按主体比例的 40/72/104/156 长边方案，限制在原图可用尺寸内；像素画提供原始逻辑尺寸。智能像素上限提高到 156，普通图片默认比例长边最多 104；自定义支持 1–208 格。图片解码长边上限提高到 2048。
- **细节**：角色精细采样保留单格稳定主色和足量深色轮廓；平涂插画智能推荐不再使用照片抖动/降噪。精细限色按频率与色差共同选色，保护眼睛等稀有特征色。像素识别错相采样，避免固定步长跳过所有边界。
- **多图**：每张上传/裁剪图片持有独立设置；仅重算输入发生变化的图，未变化图的改色历史不被覆盖。提供“复制为另一尺寸”；取消后迟到的结果不回填。
- **导出**：完整 PNG 图纸含四边逐格坐标、色号、5 格辅助线、物理分板线、颜色与数量清单；清单也计入 Canvas 内存预算。移除原来覆盖格内色号的分块字母。PDF 沿用分板打印并读取图纸自身板型。
- **验证**：新增 15 个测试覆盖比例、透明裁边、2/4/6/8 倍像素画、57×60 自定义、细轮廓、透明 RGB、小面积眼睛色、独立设置与编辑、取消结果、图纸坐标/清单和 208×208 导出预算。全量 181/181 + 类型检查 + 生产构建通过。
- **实图**：亚古兽去背景后 104×92 / 156×138；同图副本自定义 57×60 不影响 156×138 版本；导出 4960×4631 PNG 可读、眼睛绿色保留。另验证太一默认 50×104。375px 窄屏内容无页面横向溢出，浏览器日志无错误。
- **剩余边界**：低清原图无法自动变成手工重绘质量；复杂背景/压缩彩边仍需编辑。自动分类不承诺所有角色正确识别，用户可显式选“精细角色”。
- **发布**：`a51df85` 已推送 `origin/main`，VPS 备份 `/var/www/image2pindou.backup-20260907-004236`；Nginx 检查/重载、关键产物 SHA-256 和公网资源检查通过。线上亚古兽去背景及 156×138 精细生成通过，控制台无错误；旧 PWA 首次打开仍显示旧缓存，刷新后已切换新版。

## 2. 智能化（P1 遗留）

### 2.2 自动抠图增强（P2，🟡 纯色底正确度部分完成）

- **现状**：复杂背景自动走 `@imgly/background-removal`（WASM，24MB 懒加载），简单纯色背景走 `src/domain/backgroundRemoval.ts` 自适应泛洪；裁剪入口已提供智能去背景，但上传缩略图仍无独立「一键抠图」入口，复杂掩码也无显著度中心先验。
- **目标**：上传入口提供「自动抠图」按钮；分割结果更稳。
- **方案**：
  1. `UploadPanel.tsx` 每张缩略图加「自动抠图」操作（复用现有转换管线里的 `removeBackground`）。
  2. 增强：边缘引导 + 显著度中心先验 —— 对 WASM alpha 掩码做形态学开运算去孤立噪点，再以图像中心先验修正离群前景（离中心极远的连通域若面积占比小则剔除）。
  3. 抽纯函数 `src/domain/mask.ts`：`refineMask(mask, {centerPrior, minAreaRatio})` 并单测。
- **验收**：带杂点的抠图测试图，修正后前景掩码连通、无孤立噪点；`mask.ts` 单测覆盖噪点剔除/中心先验。
- **风险**：WASM 首次加载慢（24MB）——保留懒加载与进度提示；不要在首屏预取。
- **2026-08-03 部分实施**：纯色路径新增高饱和封闭背景孔洞识别，解决动漫黑色轮廓围住蓝/绿背景后残留的问题；用面积阈值保留微小主体同色细节，并禁用于白色等中性底。透明像素关闭保留时统一先合成白底，避免隐藏 RGB 产生黑底。剩余工作仍是独立上传入口和复杂 WASM 掩码的中心先验/形态学细化。
- **验证**：新增合成色键孔洞、中性白底主体细节和透明量化回归；真实 `亚古兽.jpg` 去背后封闭蓝底消失，智能推荐后保持透明且无黑底。

### 2.5 自动描边建议（P2，✅ 2026-08-03 已发布）

- **现状**：`outline` 参数需手动开启；动漫/像素画开启后效果好，但用户不知道何时该开。
- **目标**：自动检测高对比轮廓并「建议」开启 outline（不强制，展示在智能推荐差异列表）。
- **方案**：
  1. `src/domain/recommend.ts` 的 `analyzeSource` 增加轮廓占比指标：降采样后对亮度梯度做阈值统计（复用 `edgeSharpness` 思路，另算「强对比轮廓占比」）。
  2. `recommendSettings` 增加 `outline` 推荐分支：强轮廓且非照片 → `outline: true`；推荐框将自动出现「描边 关 → 开」差异项。
  3. 若用户手动已开，则不提示。
- **验收**：高对比动漫线稿测试图推荐 `outline:true`；纯照片不推荐；新增单测断言两类输入。
- **风险**：低；阈值需调参避免误报（可用回归测试图固化）。
- **实施结果**：`analyzeSource` 新增强对比轮廓占比；`recommendSettings` 仅对高轮廓、非照片素材建议开启描边，照片和低轮廓素材保持关闭，差异沿用智能推荐面板展示。
- **验证**：`domain-recommend.test.ts` 新增高对比线稿与照片两类回归断言。

### 2.6 语义颜色保护（P2，未开始）

- **现状**：压缩色数时（`maxColors`）肤色/高光等小面积但重要的区域可能被大区域同化，导致脸部「花屏」或高光丢失。
- **目标**：识别肤色/高光区域并优先保留其主色。
- **方案**：
  1. `src/domain/simplify.ts` 或新 `src/domain/saliency.ts`：亮度+色相先验标记「保护区域」像素（肤色：Lab a/b 范围；高光：L 高且饱和度低）。
  2. 调色板构建时，对保护区域颜色赋予加权票（现有显著度感知已对「高对比稀有色」留预算，扩展为含肤色/高光）。
  3. 纯函数 + 单测：构造含肤色的合成图，断言压缩后肤色桶保留。
- **验收**：合成「大背景 + 小面积肤色块」图，`maxColors=8` 时肤色主色仍在最终色板；单测覆盖。
- **风险**：肤色先验在卡通/滤镜下可能失效；只做「优先保留」，不强制，可被用户手动覆盖。

> 本节合并为一个分阶段规划。**阶段 0 已在本轮完成**，阶段 1–4 需要后端，待用户确定托管方案和部署授权后再做。

#### 3.6.1 参考：pixel-beads.com 的做法（2026-11-03 查看）

- **作品展示页（/showcase）**：作品卡片有缩略图、作品名、作者 ID、“精选”标记、浏览数；按分类筛选（卡通、动漫、游戏、像素、动物、萌宠、节日限定、新手入门、进阶挑战），可切“最新发布”；卡片可“打开图纸”。投稿入口目前跳到联系页，没有自助投稿流程。
- **会员（/membership）**：图纸生成、编辑、导出都免费；一次性付费的“网页永久会员”提供不限量的私密云端图纸、跨浏览器 / 设备同步、免广告；另有含 App 的全平台会员和单独售卖的专题图纸合集。
- **对我们的启发**：核心工具保持免费、无需登录；账号的价值在于**云端保存 + 跨设备同步**，图库的价值在于**灵感浏览 + 一键导入成自己的图纸**。

#### 3.6.2 与现有架构的关系

- 现在是纯静态前端：图片只在浏览器里处理，草稿和库存存在本机。账号和图库需要新增后端（账号、数据库、文件存储、审核后台），并要更新隐私说明（“不上传原图”可以保留，但图纸和账号信息会上传）。
- **登录不能成为使用门槛**：不登录也能完整地生成、编辑、导出；只在“同步到云端”“分享到图库”时才要求登录。
- **复用本轮的图纸文件格式**：`src/domain/projectFile.ts`（`image2pindou-designs` v1）就是云端存储、图库导入的数据格式，前后端共用一套校验。

#### 3.6.3 分阶段计划

| 阶段 | 内容 | 需要后端 | 状态 |
|---|---|---|---|
| 0 | 本机备份：图纸文件导出 / 导入、库存 CSV 导出 / 导入 | 否 | ✅ 本轮完成 |
| 1 | 账号：注册、登录、退出、找回密码、注销账号（删除全部数据） | 是 | 待定 |
| 2 | 云端同步：私密图纸、库存、色卡套装偏好在多设备间同步 | 是 | 待定 |
| 3 | 作品图库：提交分享 → 管理员审核 → 公开展示；分类、精选、浏览数、“导入到我的图纸” | 是 | 待定 |
| 4 | 互动与运营（可选）：收藏、点赞、作者主页、举报；会员 / 付费额度 | 是 | 视需要 |

**阶段 1 · 账号**
- 登录方式（按实现成本从低到高）：邮箱 + 一次性验证码 / 魔法链接（推荐起步，无需存密码）→ 邮箱 + 密码 → 手机短信（需短信服务商，面向大陆用户通常还需备案主体）→ 微信登录（需企业认证的微信开放平台账号）。
- 会话：HttpOnly + Secure + SameSite=Lax 的会话 Cookie，服务端存会话表，可在“设备管理”里逐个退出。
- 必备：隐私政策与用户协议页、注销账号（立即删除个人数据和私密图纸）、导出我的全部数据（复用阶段 0 的文件格式）。

**阶段 2 · 云端同步**
- 同步对象：图纸（矩阵 RLE 压缩 + 设置 + 标题）、库存颗数、色卡套装偏好。原图不上传。
- 冲突策略：每张图纸带 `updatedAt` 和版本号；同一张图纸两台设备都改过时，提示“保留本机 / 保留云端 / 两份都留”，不静默覆盖。
- 离线优先：本机仍是主副本（配合 5.3 的 IndexedDB），联网后后台同步；未登录用户行为不变。
- 额度：免费账号先给一个宽松上限（例如 50 张云端图纸），超出提示整理；是否做付费会员放到阶段 4 决定。

**阶段 3 · 作品图库 + 审核**（即原 3.6 的“分享 + 管理员审核”）
- 只分享图纸，不上传原图：提交内容为色号矩阵、尺寸、色卡套装、用豆清单、标题、昵称、分类标签，以及由矩阵渲染的缩略图（WebP）。
- 流程：提交 → `pending` → 管理员在 `/admin` 预览（缩略图、逐格图纸、用豆清单、提交人、举报记录）→ 批准 `approved` / 拒绝 `rejected`（附理由，作者可见）→ 图库只展示 `approved`；作者可随时撤回，管理员可下架。
- 图库页：瀑布流缩略图；按分类（参考站的 9 类起步）、尺寸、色数、所需套装筛选；“最新 / 精选 / 最多导入”排序；详情页可预览图纸和用豆清单，“导入到我的图纸”直接生成本机草稿，“按我的库存检查缺多少”复用现有缺豆计算。
- 防滥用：提交限频 + 人机校验（如 Cloudflare Turnstile）、尺寸 / 体积上限、标题敏感词过滤、举报入口。
- 版权：提交时勾选“原创或已获授权 / 同人作品注明原作”；同人作品必须填写原作名称；收到权利人投诉时下架。

**阶段 4 · 可选**：收藏、点赞、作者主页、评论（评论审核成本高，建议最后做）；会员和支付（微信 / 支付宝支付需要经营主体，海外支付需另行评估）。

#### 3.6.4 技术方案选项（待用户决定）

| | A. Cloudflare Workers + D1 + R2（推荐） | B. 现有服务器上 Node + SQLite | C. Supabase（托管 Auth + Postgres + Storage） |
|---|---|---|---|
| 运维 | 无服务器，免维护 | 需要自己维护进程、备份、升级 | 无服务器 |
| 账号 | 自建（邮箱验证码 + 会话表），邮件走第三方发信服务 | 自建 | 自带邮箱 / 第三方登录 |
| 管理后台保护 | Cloudflare Access | nginx 基本认证或自建管理员角色 | 行级权限 + 管理员角色 |
| 大陆访问 | 一般，视域名和线路而定 | 取决于服务器位置；境内服务器需备案 | 境外节点，大陆访问不稳定 |
| 成本 | 免费额度足够起步 | 已有服务器，增量成本低 | 免费额度有限，超出按量付费 |

- **体积估算**：一张 104×104 图纸 RLE 后约 2–20 KB，缩略图约 10–30 KB；1 万张作品约 0.5 GB 以内，D1 / SQLite / R2 都没有压力。
- **数据表（草案）**：`users`、`sessions`、`designs`（owner、标题、尺寸、套装、矩阵 RLE、用豆 JSON、`visibility`: private / pending / public / rejected、`featured`、`viewCount`、`importCount`、时间戳）、`gallery_reviews`（审核记录与理由）、`tags`、`reports`；阶段 4 再加 `favorites`、`likes`。
- **接口（草案）**：`POST /auth/email-code`、`POST /auth/verify`、`POST /auth/logout`、`DELETE /me`、`GET /me/export`；`GET/PUT/DELETE /designs/:id`、`GET /designs?updatedSince=`；`POST /gallery/submissions`、`GET /gallery`、`GET /gallery/:id`、`POST /gallery/:id/import`、`POST /gallery/:id/report`；`GET /admin/submissions?status=pending`、`POST /admin/submissions/:id/approve|reject`、`POST /admin/designs/:id/takedown`。
- **前端**：顶栏加“登录 / 我的账号”；新增路由（图库、作品详情、我的云端图纸、账号设置、隐私政策；管理后台单独入口）；需要引入前端路由（hash 路由即可，静态托管无需改服务器）。

#### 3.6.5 待用户决定

1. 托管方案 A / B / C，以及正式域名、是否面向大陆用户（决定是否需要备案和境内服务器）。
2. 登录方式：先只做邮箱验证码，还是一开始就要手机号 / 微信。
3. 是否允许不登录匿名投稿（建议不允许，便于追责和撤回）。
4. 同人作品的公开规则、署名要求、管理员人选和登录方式。
5. 是否做付费会员或额度限制。
6. 上线所需的部署授权（后端服务、数据库、域名 / DNS 变更都需单独授权）。

#### 3.6.6 验收（实施时）

- 不登录可完整使用现有全部功能；登录后两台设备的图纸和库存一致，冲突时有提示而不是静默覆盖。
- 注销账号后其数据从数据库和存储中删除，公开作品同时下架。
- 投稿后后台可见、前台不可见；批准后前台可见；拒绝 / 撤回 / 下架后前台不可见。
- 从图库导入的图纸与提交时的矩阵逐格一致；全流程没有原图上传请求。
- 限频与人机校验生效；未登录或非管理员访问管理接口返回 401 / 403。

## 4. 工程化（P2 遗留）

### 5.1 App.tsx hooks 化（P2，domain 层已拆，hooks 未做）

- **现状**：`src/domain/drafts.ts`、`src/domain/conversionCoordinator.ts` 已把纯逻辑抽出（Round 2），但 `App.tsx`（约 755 行）仍集中大量 state/ref/effect。
- **目标**：拆出可单测 hooks：
  - `useConversionWorker`（worker 生命周期/进度/取消，内部用 `conversionCoordinator` 状态机）；
  - `useDesignDrafts`（草稿 CRUD + 持久化）；
  - `useInventory`（库存 + 差缺，内部用 `shortfall.ts`）；
  - `useProjectStats`（统计口径，配合 1.9）。
- **验收**：每个 hook <200 行；App.tsx 净减 150+ 行；`npm test` 全绿（hooks 用 Testing Library `renderHook` 覆盖关键路径）。
- **风险**：中。必须保持行为逐字节等价——先纯重构（不动 JSX），再跑冒烟对比截图/交互。

### 5.2 Canvas 分层渲染（P2，未开始）

- **现状**：`src/components/DesignPreview.tsx` 每编辑一格全量重绘。
- **目标**：离屏底图（背景/已完成格）+ 上层叠加层（当前格/预览格），编辑只重绘叠加层；缩放/平移仅 transform。
- **验收**：200×200 图逐格编辑无明显卡顿；像素级截图对比新旧渲染一致（可用合成图回归）。
- **风险**：中。注意 worker 生成大图时的内存占用；保持 `image-rendering: pixelated`。

### 5.3 IndexedDB 草稿持久化 + RLE（P2，未开始）

- **现状**：最多 6 份草稿 × 208×208 矩阵以 JSON 存 localStorage，接近 5MB 配额风险。
- **目标**：存储升级到 IndexedDB，写入防抖 500ms；矩阵 RLE 压缩。
- **方案**：
  1. 新 `src/domain/draftStorage.ts`：IndexedDB 封装（版本化 schema、`get/set/delete/clear`、Promise API），`drafts.ts` 的 `loadDesignDrafts/persistDesignDrafts` 改为异步并接 IndexedDB，localStorage 仅作兼容回退。
  2. `serializeDraft` 改为 RLE（色号连续段编码），新增 `deserializeDraft` 对称解压；保持导出 `serializeDraft/deserializeDraft` 签名向后兼容。
  3. App 内持久化 effect 防抖 500ms。
- **验收**：创建 6 份大草稿后刷新不丢、localStorage 不再超限；往返测试（save → reload → restore 等价）用 208×208 随机矩阵验证；`draftStorage.test.ts` 覆盖 RLE 编解码（含全同色/全异色边界）。
- **风险**：IndexedDB 异步化会触碰 App 启动路径，先做兼容层再切；注意 PWA 无痕模式配额。
