## 0. 一句话结论

这次 52 张图纸暴露的不是“识别不准”一个问题，而是三个连在一起的问题：

1. **识别结果没有被“核对状态”管理**：48/52 张有图例/网格差异，但保存后看不出哪些核对过，采购清单却把它当成确定需求。
2. **采购清单只按 1000 颗/包取整，没有按真实报价算钱**：净需求 186,079 颗，app 建议买 360,000 颗；按用户提供的 500/1200/4000 补充包和套装重新算，最省钱约 **¥268**，稳妥全单色号约 **¥319**，而按当前 360,000 颗清单履行约 **¥371**。
3. **批量流程被 review 卡住**：48 张要逐张点「仍然保存」，没有「全部接受」；文件夹标签和文件名也丢了。

## 3. P0：直接影响这次 52 张的使用

### P0-1 批量接受 + 未核对状态落库

**现象**

- 52 张里 48 张需要检查；`全部保存到图库` 只保存没有 review 的 4 张，剩下 48 张要逐张点「仍然保存」。
- 我这次是用 Playwright 脚本点了 47 次才存完；真实用户会放弃。
- 保存后没有 `verified` / `review` 字段：`Pattern` 模型只有 `confidence`，注释写“人工确认后置 1”，但实际只有比耶一张是 1.0；48 张未核对状态完全丢失。

**证据**

- 批量页截图：`52 完成 · 48 需要检查 · 2 不是图纸`，每个 review 项只有「检查 / 仍然保存 / ×」。
- `web/src/lib/model.ts` 的 `Pattern` 没有 `verifiedAt` / `reviewReasons`。
- DB 查询：52 条 `patterns` 中 `confidence=1` 只有比耶。

**改动**

1. **数据模型**（`web/src/lib/model.ts`）
   - `Pattern` 增加：
     - `verifiedAt?: number`：人工点过“已核对”的时间。
     - `reviewReasons?: string[]`：保存时把自动 review 理由落库，而不是只留在识别页。
     - `reviewedBy?: string`（可选，多设备时用）。
   - `confidence` 保留为“整体可信度”；另加 `colorMatch?: number`（颜色匹配度）。
   - `CountMethod` 增加 `"cell"`（格内色号为主）。

2. **批量页**（`web/src/components/pattern/BatchPanel.tsx`）
   - 每个 done 项加复选框；底部加：
     - 「接受全部并保存」：保存所有 done，写入 `verifiedAt: null` + `reviewReasons`。
     - 「只保存已核对」：只保存 `verifiedAt` 有值的项。
     - 「标记为已核对」：在 review 抽屉里，点完后 `verifiedAt=Date.now()`，`confidence` 可置 1 或保留颜色分。
   - 保留「仍然保存」作为单项快捷操作，但它**不等于**已核对：写入 `verifiedAt: null`。
   - 保存后不要因为 review 状态阻塞；用 toast 汇总“已保存 48 张，其中 48 张未核对”。

3. **图库**（`web/src/pages/Gallery.tsx`）
   - 卡片加「未核对」徽章；筛选加「未核对 / 已核对」。
   - 批量操作加「标记为已核对」。

4. **采购清单**（`web/src/pages/Shopping.tsx`）
   - 顶部提示“48 张未核对，金额可能偏差”；加「只算已核对」开关（默认关，不阻塞采购）。
   - 图纸复选框列表给未核对项加小标记。

**验收**

- [ ] 54 张批量导入 → 52 张 done；点「接受全部并保存」一次保存 52 张，不需要逐张点。
- [ ] 保存后 48 张 `reviewReasons` 非空、`verifiedAt=null`；4 张干净项也保存为 `verifiedAt=null`（算法没报警不等于人工核对）。
- [ ] 图库能筛出「未核对」48 张；点「标记为已核对」后变 0 张。
- [ ] 采购清单「只算已核对」打开时，只统计已核对项；默认关时仍然统计全部，但有提示。

### P0-2 可信度拆成“颜色匹配度 / 整体可信度”

**现象**

- 蟹老板 100%，但 review 理由写“与图上标注不符：色数、总数；2 个色号图例与网格不一致”。
- 亚古兽 100%，但 4 个色号图例与网格不一致。
- 自由 92%，但 14 个色号不一致。
- 比卡超 33/33 格内色号、校正 7 色，却只有 68%，仍被 review。
- 这说明当前 `confidence` 更像“颜色匹配度”，不是“整张图纸可信度”。

**改动**

1. **拆两个分**（`web/src/lib/recognize/assistant.ts`）
   - `colorMatch`：现有颜色匹配/网格覆盖率。
   - `overall`：颜色分 + 图例/网格差异 + 抬头差异 + 格内色号覆盖率的加权；有 review 理由时设上限（例如最多 69%）。
   - `confidence` 存 `overall`；`colorMatch` 另存，UI 同时显示。

2. **保存 review 理由**：`reviewReasons` 落库（见 P0-1），不要只在识别页显示。

3. **给出“建议采用”**
   - 每个色号/整张图标：`建议采用：格内色号 / 网格 / 图例`。
   - 判定规则：格内色号覆盖率高 → 格内色号；否则网格；图例只作对照。
   - review 表增加「采用」列，明确最终数量来自哪一列。

4. **100% 的语义**
   - 只有“无 review 理由 + 格内色号覆盖率高 + 图例/网格一致”才允许 100%。
   - 否则最高 99%，避免“100% 但需要检查”的矛盾。

**验收**

- [ ] 蟹老板不再显示 100%（有抬头/色数差异时 overall ≤69%）。
- [ ] 比卡超显示“颜色匹配 90%+ / 整体 68%”，并标“建议采用：格内色号”。
- [ ] 任一有 review 理由的图纸不会显示 100%。
- [ ] review 表有「采用」列，且与最终 `counts` 一致。

### P0-4 零库存 onboarding

**现象**

- 52 张图库卡片全「缺 X 色」；总览「库存能做 0 份」「备豆 0%」；详情页每色「缺 700 / 缺 467…」。
- 新用户导入 52 张后满屏红字，分不清“真的缺”还是“还没录入库存”。
- 这不是数据错误，是“库存未初始化”和“库存=0”被当成同一件事。

**改动**

1. **区分状态**
   - 增加 `inventoryInitialized`（有 `txns` 或用户点过“开始录入”即为 true）。
   - `stock=0` + 未初始化 → 显示「未录入库存」，不显示「缺」。
   - `stock=0` + 已初始化 → 才显示「缺」。

2. **首次引导**
   - 总览/采购页首次进入时给两个按钮：
     - 「录入现有豆盒」→ 去 `#/inventory`。
     - 「跳过，先看需求」→ 本次会话不再提示。
   - 图库卡片在未初始化时显示「未入库」，不显示「缺 X 色」。

3. **总览**
   - “库存能做 0 份” → “库存未录入，先入库或先看需求”。
   - “备豆 0%” → “—”。

**验收**

- [ ] 全新库（无 txns）导入 52 张后，图库不再满屏「缺 X 色」，显示「未入库」。
- [ ] 点「跳过，先看需求」后，采购清单仍能按需求算，不显示“缺货”红色。
- [ ] 录入任意一笔库存后，状态切回正常「缺/够」。

## 4. P1：识别与数据质量

### P1-1 网格总数硬校验

**现象**：全力以赴图上 34×30=1,020 格，却数出 2,348 颗；这次靠“图例不一致”被拦下，但没有明确提示“网格可能过细”。

**改动**（`web/src/lib/recognize/assistant.ts`）

- 增加硬校验：`sum(counts) <= rows * cols`；违反时：
  - 降采样/重新检测更粗的网格；或
  - 在 review 顶部明确写“网格 34×30，最多 1,020 格，但数出 2,348 颗，请确认网格”。
- 把 `rows/cols` 和 `sum(counts)` 显示在 review 头部，不只放在详情页。

**验收**：全力以赴这类图会被显式标记；不会只显示“图例不一致”。

### P1-2 格内色号成为主证据

**现象**：比卡超 33/33 格内色号、校正 7 色，仍因图例 12 个色号不一致被打到 68%。

**改动**（`web/src/lib/recognize/assistant.ts`）

- 计算 `cellCoverage = 读出格内色号的格数 / 非背景格数`。
- 采用优先级：`cellCoverage >= 0.9` → 格内色号；`>=0.6` → 网格 + 格内校正；否则网格/图例。
- `method` 增加 `"cell"`；UI 显示“格内色号 33/33（100%）”。
- review 表加「采用」列；图例差异只作为提示，不再单独拉低整体分。

**验收**：比卡超的最终数量明确标“格内色号”；review 理由仍保留图例差异，但不再让用户误以为网格结果不可信。

### P1-3 文件夹标签 / 批量改名 / 查重

**现象**

- 用「选择多张图片」时浏览器拿不到 `webkitRelativePath`，52 张标签全空（截图可见）。
- 哈希文件名 `02da54…`、`7a790f…` 原样成为图纸名。

**改动**

- 批量页把「选择文件夹」设为主按钮；文案写“保留文件夹名作为标签”。
- 支持 File System Access API（`showDirectoryPicker`）读取目录名；不支持时退回文件夹选择。
- 导入后加「按文件夹分组」「批量改名」：
  - 用文件名/文件夹名生成名称；哈希名检测（32/64 位 hex）提示改名。
- 入队时用 SHA-256 查现有 `images`，已存在则标记「已存在」，支持跳过/合并。

**验收**：选文件夹导入 52 张，标签自动为 6 个系列；哈希名有提示；重复导入不产生重复图纸。

### P1-4 notchart 批量生成

**现象**：2 张不是图纸，只能逐张点「用它生成图纸」。

**改动**：队列加「把这些不是图纸的图批量生成图纸」，选板子尺寸/色数；或「存为灵感」保留原图，不进入采购。

**验收**：2 张 notchart 可一次生成/保存，不用逐张。

### P1-5 中文图例 OCR

**现象**：只带 `@tesseract.js-data/eng`；游戏王/高达中文图例多，平均可信度 66%/64%。

**改动**

- 加 `chi_sim` 训练数据，或维护中文色名 → MARD 色号的小词典。
- 检测到中文图例时，明确提示“中文图例未 OCR，当前按网格/格内色号”；不要静默降可信度。

**验收**：中文图例的图纸 review 理由能区分“中文未识别”与“数量不一致”。

### P1-6 重复导入 / 同步体积

**现象**：无 SHA-256 查重；52 张 63MB，手机同步偏重。

**改动**

- 入队时查 `images` 哈希；已存在则跳过/合并。
- 保存缩略图（如 512px WebP）+ 原图按需；矩阵压缩；增量同步；设置页显示本次同步体积。

**验收**：重复导入 0 新增；同步体积明显下降；原图仍可查看。

### P1-7 同页数字口径统一

**现象**：比卡超 review 顶部写「12 个色号不一致」，助手时间线写「8 个色号不一致」。

**改动**：统一为“12 个色号有差异，其中 8 个可对比”；或在时间线注明“仅统计图例/网格都有数字的色号”。

**验收**：同一页两个数字不再矛盾。

## 8. 假设与待确认

1. **套装 1200 颗是“每色 1200 颗”**，不是整盒 1200 颗。如果是整盒，套装方案全部作废，需要重算。
2. **套装 221/265/295 色与 MARD 色号是否一一对应**未知；对不上就不能按色号精确买，只能按颜色近似。这是采购方案最大的风险。
3. **4000 颗 ¥2.17 仅 A–M 色系**；本分析按色号首字母 A–M 判断。如果卖家 A–M 的定义不同，需要重算。
4. **500 颗 ¥1 的“10 包以上可备注色号”**按整单满 10 包处理；本方案 500 包数 158/16，满足。
5. **1200 颗 ¥1.26–1.5**：主方案按 1.26 算；1.5 的敏感性见报告。
6. **价格不含运费/打包费**；实际下单要加。
7. **识别数量是估算**：48/52 张有图例/网格差异，31/52 <70%；采购前先核对用量最大的几张（天女兽、妖精战士、黑魔导女孩、00R、黑魔导士等）。
8. **221 套装的“最优缺 8 色”是一组解**：G16、H5、C7、H13、H16、H3、H6、H9；由于多色覆盖价值相同，换一组同价值的 8 色成本几乎不变。实际以套装色表为准。

## 9. 建议实施顺序

1. **P0-1 + P0-2**（1–2 天）：先让 52 张能一次保存、能看出是否核对；这是所有后续统计的信任基础。
